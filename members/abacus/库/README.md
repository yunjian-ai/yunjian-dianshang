# 店铺数据底座 · 三本会长的账（格式 v0.1，2026-10-28）

> 给人看：这是算盘的底子。除了数据表，还有三本会自己更新的账：**A 平台规则库**（官方规则）、**B 自动化地图**（后台每一步怎么点）、**C 经营决策库**（货盘、政策、主人定的规矩）。规则变了、按钮挪了、政策改了，都按同一套办法更新；脚本里的费率和上限一律从账里读，不写死。
> 给 AI：照下面的格式写卡；改任何一张卡都先写变更单（`模板/变更单.md`），再按第 5 节走完六步；每本账的 `变更记录.md` 只追加不删。

## 1. 文件夹
装好以后在 `~/.yunjian/abacus/`：
```
库/                    我们给的，更新时整份换新
  README.md            本文件：格式和迭代机制
  平台规则库/          R-<块>-<三位号>-<短名>.md，一条规则一张卡；变更记录.md
  自动化地图/          M-<后台>-<三位号>-<短名>.md，一个后台操作一张卡；变更记录.md
  模板/                决策卡、变更单、成本表模板
  默认值/              服装店默认经营决策（主人没说时先用）
店铺/<店名>/           主人自己的，更新永不覆盖
  经营决策库/          D-<类>-<三位号>-<短名>.md；变更记录.md
  底座数据/            成本表.csv 等
  账单/                后台导出的原表（订单表只留 25 列，不含收件人信息）
  变更单/              B-<三位号>.md，每次改动一张
  报告/                每期的逐单账和报告
```
指纹脚本在技能 abacus-base 里（`指纹.py`）。
编号块：JS 结算和钱、SP 商品和上架、LM 精选联盟和达人、SH 售后、GZ 通用规则。后台：DD 抖店、BY 精选联盟（百应）、LP 罗盘、QC 千川。决策类：HP 货盘、ZC 经营政策、DR 达人服务。

## 2. A 平台规则库：每张卡
开头一段（脚本读这一段）：
```
---
编号: R-JS-001
标题: 结算账单的结构和结算金额怎么算
状态: 生效            # 生效 / 已停用（被哪张替代写在「替代」）
版本: 1
官方链接: https://...
页面更新日期: 2024-10-16      # 官方页面上写的
核对日期: 2026-10-28          # 我们最后一次打开对过的日期
正文指纹: 9f3c...             # 官方正文去掉导航后的 sha256 前 12 位，巡检比对用
生效日期: 2024-10-16          # 规则开始管用的日期；算账按订单日期取当时生效的那一版
影响: [算盘/逐单算账]
参数:                         # 脚本读的数，没有就写 {}
  平台服务费基数: [用户实付, 平台补贴, 达人补贴, 抖音支付补贴, 抖音月付营销补贴, 以旧换新抵扣, 银行补贴, 平台补贴运费]
替代: 无
---
```
正文：**要点**（换成自己的话转述，不照抄原文）→ **我们怎么用**（哪个公式、哪个判断）→ **容易错的地方** → **原文位置**（第几节）。官方原文全文只存本机 `资料/官方原文/`，不上云。

## 3. B 自动化地图：每张卡
```
---
编号: M-DD-001
标题: 导出结算账单明细
后台: 抖店 fxg.jinritemai.com
入口: 抖店后台 → 资金 → 结算账单
类型: 只读                    # 只读 / 会改东西（会改东西的，换新路线前必须主人点头）
状态: 可用                    # 可用 / 待修 / 已停用
版本: 1
最后走通: 2026-10-28
连续失败: 0
影响: [算盘/取数]
---
```
正文是步骤表，**按按钮上的字和页面标题找，不写屏幕坐标**：
| 步 | 做什么 | 找什么（页面上的字） | 应该看到 |
|---|---|---|---|
下面附：**常见岔路**（弹窗、二次确认、报表要排队生成）、**停下的情况**（验证码、二维码、要密码）、**走通记录**（日期、谁走的、成功／失败、失败时页面上写的什么）。

状态: 生效                    # 生效 / 已停用
版本: 1
生效日期: 2026-10-17

正文：内容、为什么、例外。货盘（HP）一款一张卡，状态写「在售／主推／新品／清仓／下架」，每次变化加一行历史，不删旧行。

## 5. 一套迭代机制（三本都一样）
1. **发现**：①每周巡检（规则卡逐张打开官方链接，比页面更新日期和正文指纹——**只取正文块（`工具/取原文.mjs`），指纹不同先隔一会儿重取一次，两次都变才算真改了**，避免页面没加载全造成误报；地图卡里超过 14 天没走过的，空走一遍只读步骤；决策卡超过 90 天没动的，问主人还算不算数）②干活撞上（找不到按钮、后台提示和卡不一样、算出来和结算账单对不上）③主人说「平台改了」「以后……」。
2. **变更单**：照 `模板/变更单.md` 写：旧的怎么写、新的怎么写、出处、影响哪些公式／技能／地图、旧订单要不要重算。
3. **确认**：规则卡——附官方原文那一段，请主人看一眼点头；地图卡只读路线——新路线自己试走通过就换上，事后告诉主人；**会改东西的路线、所有决策卡——主人点头才生效**。
4. **生效**：旧卡状态改「已停用」（不删），新卡版本加一、写生效日期；`变更记录.md` 追加一行。脚本按订单日期取当时生效的那一版。
5. **回归**：受影响的考题和自测重跑，过了才算换好。
6. **告诉主人**：一条一句：什么变了、影响什么、已换好还是等您点头。

越用越好：地图卡记「连续失败」和走通记录，常坏的路线巡检加密；每月出一份底座变化记录。
